# Устройство raf

Код сгруппирован вокруг работы с сообщениями. Адаптеры HTTP, Kafka и Protobuf
находятся внутри модуля `message`. Приложение собирается в `app.App`.

## Структура

```text
cmd/raf/main.go                  — конфигурация, логгер, сигналы, New → Run
internal/
  app/app.go                    — сборка зависимостей, запуск и остановка
  config/                       — YAML, переменные окружения и проверка настроек
  message/
    model/                      — сообщения, заголовки, позиции и сведения о топиках
    usecase/                    — сценарии, их входные данные и интерфейсы
    adapter/
      http/                     — маршруты, параметры, HTTP-статусы и JSON
      kafka/                    — публикация и чтение через kafka-go
      protobuf/                 — загрузка контрактов и преобразование данных
```

## Зависимости

- `model` использует только стандартную библиотеку.
- `usecase` использует модели и собственные интерфейсы `Publisher`, `Reader`, `TopicCatalog`, `Codec`.
- Адаптеры реализуют эти интерфейсы или вызывают сценарии. Сценарии не импортируют адаптеры.
- `app` знает конкретные реализации и связывает их между собой.

Типы `kafka-go` остаются внутри Kafka-адаптера. HTTP-обработчики получают интерфейс
сценариев, а не всё приложение. В моделях нет JSON-тегов: формат HTTP-ответа
описывается отдельно в `adapter/http/response.go`.

## Как проходит запрос

Публикация:

1. HTTP-обработчик проверяет Content-Type, размер тела и заголовки.
2. `usecase.Service.Publish` выбирает тип: явно указанный или настроенный для топика.
3. Кодек преобразует ProtoJSON в бинарное сообщение.
4. Kafka-адаптер публикует его и возвращает подтверждённую позицию.
5. HTTP-адаптер формирует ответ с топиком, партицией и offset.

Чтение:

1. HTTP-обработчик разбирает параметры и задаёт стандартный limit.
2. `Service.Inspect` проверяет тип и limit, затем вызывает читатель.
3. Kafka-адаптер собирает последние доступные записи партиций.
4. Сценарий декодирует записи по отдельности. Ошибка одной записи сохраняется
   рядом с её исходными байтами и не мешает вернуть остальные.
5. HTTP-адаптер формирует JSON, включая Base64 для бинарных значений и ошибок декодирования.

У сообщения `Value == nil` означает tombstone. Пустой срез, отличный от nil,
означает сообщение из нуля байт. Это различие сохраняется во всех слоях.

## Где искать алгоритм чтения

- `kafka/reader.go` — получение партиций, параллельное чтение, общий порядок и limit.
- `kafka/partition_reader.go` — диапазоны offset, поиск от конца партиции,
  чтение окон и обработка удаления записей во время чтения.
- `kafka/records.go` — обход пакетов, служебные записи, копирование данных
  и освобождение буферов.

Диапазоны полуоткрытые: `[first, end)`. Разница offset не равна числу сообщений:
после compaction остаются пропуски. Алгоритм расширяет поиск к началу партиции,
если в текущем окне недостаточно записей.

## Жизненный цикл

`config.Load` применяет значения по умолчанию, затем YAML-файл из `RAF_CONFIG_FILE`,
затем непустые переменные окружения. Формат YAML описан отдельно в `config/file.go`.
Каталоги импортов из файла считаются от его расположения; переопределения из окружения —
от рабочего каталога процесса.

`Service.Example` вызывает генератор в `protobuf/example.go`, который обходит
дескрипторы с ограничениями глубины и числа полей. `Service.ListTopics` и
`Service.DescribeTopic` объединяют метаданные Kafka с настроенными типами raf.
Получение примера не обращается к Kafka; каталог читает метаданные и границы партиций.

`app.New(ctx, cfg, logger)` проверяет настройки, загружает контракты, проверяет
сопоставления топиков и собирает зависимости. Контекст здесь ограничивает сборку.

`App.Run(ctx)` запускает HTTP-сервер и ожидает отмены контекста или ошибки сервера.
После этого HTTP-запросы и закрытие брокера разделяют 10 секунд на завершение.
По истечении срока контексты запросов отменяются, соединения HTTP закрываются,
а ожидание публикаций прекращается.

`Run` вызывается один раз и закрывает ресурсы даже при ошибке открытия порта.
Сигналы ОС обрабатываются в `main`: первый запускает плавную остановку,
повторный позволяет завершить процесс немедленно.

## Проверки

Тесты сценариев используют подставные реализации интерфейсов. Тесты HTTP проверяют
параметры и ответы; дополнительные проверки связывают обработчики со сценариями
и настоящим Protobuf-кодеком. Тесты адаптеров покрывают особенности библиотек,
а интеграционные тесты Kafka проверяют реальную публикацию и чтение.

Команды запуска приведены в разделе Development checks основного README.
